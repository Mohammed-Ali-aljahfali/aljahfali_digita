# ربط Supabase والنشر والتراجع الآمن

آخر مراجعة: 26 نوفمبر 2026. هذه تعليمات تنفيذ لمالك المشروع؛ لم تُنفذ على قاعدة الإنتاج. اجتازت الشيفرة اختبارات محلية معزولة، وتبقى تجربة Supabase الفعلية والبريد وStorage شرطًا قبل البيع.

## 1. نقطة الاستعادة ومراجعة القاعدة

- احتفظ بنسخة من ملفات الاستضافة ونسخة من قاعدة البيانات تشمل المخطط والبيانات والأدوار والسياسات. انسخ ملفات Storage بصورة مستقلة؛ نسخة قاعدة البيانات وحدها لا تضم محتوى الملفات. تحقّق من إمكانية الاستعادة إلى مشروع اختبار قبل تعديل الإنتاج.
- أرشيف `.backups/pre-store-upgrade-c2425ac.zip` نقطة استعادة لملفات الموقع فقط، وليس لقاعدة البيانات.
- استخدم مشروع Supabase تجريبيًا مستقلًا ببيانات اختبار معزولة. لا تنسخ بيانات العملاء الحساسة إلى اختبار عام.
- راجع سياسات الجداول المستهدفة وStorage والدوال الموجودة قبل الترحيل. لا تشغّل `database_schema.sql` القديم؛ يحتوي صلاحيات عامة غير آمنة واحتُفظ به للمراجعة التاريخية.

استعلام مراجعة للقراءة فقط في SQL Editor:

```sql
select schemaname, tablename, policyname, roles, cmd, qual, with_check
from pg_policies
where schemaname in ('public', 'storage')
order by schemaname, tablename, policyname;
```

## 2. تطبيق الترحيل في التجربة

افتح SQL Editor في مشروع **التجربة** ثم نفّذ كامل الملف `supabase/migrations/202611250001_secure_store.sql` مرة واحدة. الملف محاط بمعاملة، ويتضمن سجل إصدار ويمكن إعادة تنفيذه دون إعادة ضبط المنتجات أو الأسعار.

إذا ظهر `UNREVIEWED_POLICY` فتوقّف وراجع السياسة المذكورة وسبب وجودها. لا تتجاوز الحارس ولا تحذف السياسات عشوائيًا. الترحيل يتعرف على السياسات القديمة المعروفة فقط، ويرفض تجاهل السياسات الأخرى. إذا توقفت المعاملة فراجِع حالة SQL Editor ونفّذ `ROLLBACK` عند الحاجة قبل إعادة المحاولة.

تحقّق من سجل الإصدار ومن أعداد المنتجات والأسعار والطلبات السابقة بعد الترحيل:

```sql
select * from public.store_schema_migrations;
select count(*) as products from public.products;
select count(*) as orders from public.orders;
```

الطلبات القديمة تبقى محفوظة ببياناتها؛ لا تُحوّل إلى مدفوعات مؤكدة بناءً على حالتها التاريخية. راجعها من مصادرها قبل أي تسوية. لا تُنشأ طلبات اختبار داخل الإنتاج.

## 3. إعداد المتصفح والحسابات

ضع رابط مشروع التجربة ومفتاحه العام `publishable` أو `anon` في `assets/js/store-config.js`. لا تضع `service_role` أو `sb_secret` أو كلمة مرور قاعدة البيانات في هذا الملف أو في لوحة المتجر.

في إعدادات Supabase Auth:

- اضبط Site URL على عنوان الموقع التجريبي، وأضف عناوين العودة المستخدمة: `/account.html` و`/login.html?recovery=1`. أضف الأصل المحلي فقط عند اختبار الدخول المحلي، ثم أزل العناوين غير المطلوبة عند إعداد الإنتاج.
- اختبر التسجيل وتأكيد البريد والدخول والخروج واستعادة كلمة المرور؛ تأكد من إعداد البريد وحدود الإرسال في مشروعك.
- اترك `auth.googleEnabled=false` حتى إعداد مزود Google وروابط عودته واختبار الدخول بنجاح.

أنشئ حساب المالك عبر التسجيل، ثم راجع UUID الخاص به في Authentication. من SQL Editor الموثوق فقط، استبدل القيمة التالية بمعرّف الحساب الذي تحققت منه:

```sql
update public.profiles
set role = 'admin'
where id = 'OWNER_USER_UUID'::uuid
returning id, email, role;
```

يجب أن يرجع حساب المالك المقصود وحده. لا تستخدم البريد أو اسم العميل لتخمين الحساب. بعد الدخول كمدير، تُدار الأدوار اللاحقة من لوحة الإدارة، ويمنع النظام إزالة آخر مدير عبر واجهته.

## 4. رفع سند التحويل

انشر دالة `upload-payment-receipt` من مجلد المشروع باستخدام Supabase CLI مثبت من المصدر الرسمي. مثال موجّه صراحةً إلى مشروع التجربة، مع استبدال `STAGING_PROJECT_REF`:

```powershell
supabase login
supabase secrets set RECEIPT_ALLOWED_ORIGINS=https://staging.example.com --project-ref STAGING_PROJECT_REF
supabase functions deploy upload-payment-receipt --project-ref STAGING_PROJECT_REF
```

`staging.example.com` مثال في هذا الدليل فقط؛ استبدله بالأصل الحقيقي (البروتوكول والنطاق والمنفذ، دون مسار أو شرطة نهائية). تقبل `RECEIPT_ALLOWED_ORIGINS` عدة أصول مفصولة بفواصل. أضف `http://127.0.0.1:4173` عند تجربة الواجهة المحلية على مشروع التجربة. لا تستخدم `*`.

اترك `verify_jwt=true` كما في `supabase/config.toml`؛ تتحقق الدالة أيضًا من المستخدم عبر `auth.getUser()` قبل الكتابة بامتيازات الخادم. تستخدم مفاتيح البيئة التي يوفّرها Supabase؛ تدعم `SUPABASE_URL` و`SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY` أو القواميس `SUPABASE_PUBLISHABLE_KEYS`/`SUPABASE_SECRET_KEYS` بالمفتاح `default`. لا تضعها في المصدر أو المتصفح.

الترحيل يهيئ الحاوية الخاصة `payment-receipts`. الرفع المباشر من العميل غير مسموح. تتحقق الدالة من جلسة المستخدم وملكية الطلب وحالته وحجم الملف وبنية PNG/JPEG/WebP، وتحفظ سجل الرفع. الروابط الموقعة قصيرة الصلاحية. رفع الصورة لا يؤكد الدفع؛ إرسال الإثبات يطلب مراجعة الإدارة.

## 5. تهيئة المتجر ودورة التحقق

1. راجع الكتالوج الموجود. استخدم استيراد المنتجات المفقودة من لوحة الإدارة عند الحاجة؛ لا تستبدل الأسعار المعتمدة ببيانات جديدة.
2. أدخل وسائل دفع حقيقية مع اسم المستلم ورقم الحساب والعملات وتعليمات التحويل. لا توجد أرقام حسابات تجريبية في الإنتاج.
3. راجع الباقات والمخزون وحدود الكميات والصرف والتقريب والتكاليف. الأسعار التاريخية مستقلة ويدوية افتراضيًا، وأسعار الطلبات محفوظة وقت الشراء.
4. اعتمد وصف المنتجات والضمان والسياسات قبل عرضها للعملاء. مرجع التحرير: `docs/POLICY-REVIEW.md`.
5. في مشروع التجربة فقط: اختبر مستخدمين مستقلين ومديرًا. اختبر البحث والسلة والعملات والكوبونات وإنشاء الطلب وإعادة الطلب بعد انقطاع الاتصال ورفع السند ورفضه أو تأكيده والتفعيل ومتابعة الحساب.
6. تحقق أن المستخدم لا يرى طلبات وسندات عميل آخر، ولا يعدل دوره أو السعر أو حالة الدفع، وأن الروابط الموقعة لا تمنح وصولًا عامًا للحاوية.
7. اختبر Google والبريد ورفع السند الحقيقي على المتصفح والجوال؛ هذه الخدمات لا تغطيها محاكاة الاختبارات المحلية.

## 6. التجديد والصيانة

طلب التجديد يسجل متابعة مرتبطة بالاشتراك. يشتري العميل الباقة المناسبة بطلب جديد، وتؤكد الإدارة الدفع ثم تربط رقم الطلب بالتجديد. قاعدة البيانات ترفض طلب عميل آخر أو منتج/باقة مختلفة أو الطلب الأصلي، وترفض حالة «مكتمل» قبل تأكيد الدفع.

تحديث حالة التجديد لا يغير تاريخ الانتهاء تلقائيًا. بعد تنفيذ التفعيل فعليًا، حدّث تاريخ الاشتراك من قسم الاشتراكات، ثم اعتمد المتابعة مكتملة. لا تحفظ كلمات المرور أو رموز التحقق في ملاحظات التسليم.

زر «تشغيل الصيانة» في لوحة الإدارة يستدعي `admin_run_maintenance()` بهوية المدير: يلغي الحجوزات غير المدفوعة المنتهية، ويحدّث الاشتراكات المنتهية، وينشئ إشعارات قرب الانتهاء دون تكرار. شغّله دوريًا حسب عمل المتجر. لا يوجد جدول تشغيل تلقائي منشور ضمن هذه النسخة.

`notification_outbox` طابور مستقل لتكامل واتساب المستقبلي. لا يوجد عامل إرسال فعلي، ولا تُرسل رسائل أثناء الاختبارات. تعطله لا يمنع حفظ الطلبات.

## 7. نقل النسخة المختبرة إلى الإنتاج

بعد نجاح التجربة ومراجعة المحتوى ووسائل الدفع، خذ نسخًا حديثة وتحقق من مشروع الإنتاج المستهدف. طبّق الترحيل وانشر الدالة بنفس الإصدارات المختبرة، ثم اضبط الأصول وAuth وإعدادات المتصفح الخاصة بالإنتاج. غيّر الرابط والمفتاح العام معًا.

انشر فقط صفحات HTML المستخدمة و`styles.css` و`script.js` ومجلد `assets` والأيقونات و`manifest.json` و`robots.txt` و`sitemap.xml`. لا ترفع `.git` أو `.backups` أو `.cache` أو `node_modules` أو `scratch*` أو `scripts` أو `tests` أو `test-results` أو `docs` أو `supabase` أو ملفات SQL وبيانات البيئة إلى جذر الموقع العام.

اختبر HTTPS ورؤوس الأمان وروابط الحساب وواجهات API من النطاق النهائي. إعداد الاستضافة الحالي لم يُغيّر في هذا العمل.

## 8. التراجع عند فشل التشغيل

- أوقف استقبال طلبات جديدة من الاستضافة، واحتفظ بوصول الإدارة للمراجعة. لا تعِد صفحة الطلبات القديمة التي تعتمد أسعار العميل أو صلاحيات عامة.
- انسخ البيانات والسندات التي أُنشئت بعد النشر قبل أي استعادة. الاحتفاظ بالنسخة الجديدة ضروري حتى لو ستعود إلى نسخة قاعدة أقدم.
- إذا فشل الترحيل داخل المعاملة، صحّح السبب في التجربة ثم أعد التنفيذ؛ لا تنفذ حذفًا تعويضيًا عشوائيًا.
- عند الحاجة إلى استعادة قاعدة فعلية، استعد النسخة المختبرة إلى مشروع منفصل أولًا، ثم سوِّ الطلبات والمدفوعات اللاحقة بالتعاون مع المالك قبل تبديل الخدمة.
- لا يوجد ملف down migration يحذف الكيانات التجارية، لأن ذلك قد يفقد بيانات جديدة. لا تستخدم `database_schema.sql` كطريقة تراجع؛ يعيد صلاحيات غير آمنة.
